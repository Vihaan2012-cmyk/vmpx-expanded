VMProtect notes

Knowledge reference derived from the vmpx source. Each section names the module that reveals the mechanism.

This page records what the vmpx codebase encodes about VMProtect internals: layouts it recognizes, structures it recovers, and invariants it refuses to assume. It is not a statement of how VMProtect is specified. Where a point is implied by the code but never literally asserted, it is tagged inferred.

How to read this

  • Everything is static: files are parsed and symbolically analyzed; nothing is executed.
  • The pipeline order is packing (vmpx-unpack), detection (vmpx-detect), VM analysis (vmpx-vm), lifting (vmpx-vmlift), code generation (vmpx-recompile), then PE reconstruction (vmpx-rebuild).
  • The recurring design rule is fail closed: ambiguity is kept in a report and yields no result, rather than a guess. Many doc comments say so explicitly (for example "No unknown value is invented", "it never guesses a missing operation").

Caveats

Behavior-reversible, not bit-reversible
The project's stated goal (README) is "clean, behavior-preserving devirtualized output". Replacements are rebuilt from recovered semantics, so they compute the same register state and effects; they are not the original compiler output. inferred Original instruction bytes are not recoverable from the VM bytecode, which is why no module attempts it.
Static analysis: runtime defenses never fire
No crate executes the target, and a search of the sources finds no anti-debug handling code. inferred Any VMProtect behavior that only triggers while running (debugger checks, timing checks) is therefore never exercised; the toolkit instead recovers the handlers that implement such behavior as static semantics (for example the timestamp-counter and checksum handlers below).
Current end state
For a protected input, vmpx clean still reports blockers (original entry point unrecovered, import set unproven, no devirtualized replacement image, protector sections still referenced), so it does not emit a devirtualized file. Reconstruction in this page describes what the libraries can do, not a completed devirtualization.

Packing

Module: crates/vmpx-unpack/src/lib.rs. A packed binary keeps its protected content compressed in the file; the section table still describes where that content lands in memory.

Packed sections and the PACKER_INFO table

  • Destination sections are those with PointerToRawData == 0, SizeOfRawData == 0, nonzero VirtualSize, and without the uninitialized-data flag: "initialized virtual-only" sections. They exist in the section table but have no bytes on disk. inferred Their content is filled by the protector's loader code at runtime; the code reproduces that fill statically.
  • PACKER_INFO is an array of 8-byte entries, { source_rva: u32, destination_rva: u32 }, one per destination section. It is located by scanning the whole file; there is no fixed offset.
  • A candidate is accepted only if every source_rva maps to a file byte equal to 0x00 (the code treats that as the first byte of a raw LZMA range-coder stream). At most 16 candidates are collected; the search requires exactly one validated table, otherwise it reports ambiguity or absence.
  • Two layouts are tried, legacy first; the encoded layout is only searched when no legacy table validates.
PackerLayoutKind::LegacyPlaintext

The destination RVAs are stored in the clear. Entry i validates when its destination field equals the virtual address of destination section i. The dword located 8 bytes before the table is an RVA that points at the 5 LZMA property bytes, so the properties come from the file (destination_key = None).

PackerLayoutKind::EncodedRotatingKey

Destination RVAs are obfuscated with a rotating key (next subsection). The LZMA properties are not read from the file: the fixed constant 5D 00 00 00 04 (DEFAULT_LZMA_PROPERTIES) is used.

The rotating-key scheme

For entry index i with stored value s[i], the decoded destination is:

destination[i] = s[i] XOR rotl32(key, (i * 7) & 31)

  • The key is not stored. The code derives it by assuming destination[0] equals the virtual address of each candidate destination section in turn: key = s[0] XOR seed_section_VA.
  • A key is accepted only if every decoded destination is the virtual address of a destination section and the decoded set is a permutation of those sections (no duplicates, none missing).
  • Cheap pre-filters: the first two entries' source RVAs must already validate before the full table is checked at a byte offset.

LZMA-compressed virtual-only sections

  • Each block is a headerless raw LZMA stream. The code synthesizes the 13-byte standard header: 5 property bytes plus an unpacked size of u64::MAX (unknown), then feeds the stream and relies on the end marker.
  • The stream is followed by unrelated PE bytes. A standalone decoder rejects trailing input, so on failure the code retries with exactly the number of bytes the first pass consumed up to the end marker ("evidence-derived, not a guessed compressed size").
  • Decompression is bounded: output cannot exceed the destination span, and the decoder has a 128 MiB memory limit. UnpackLimits default to a 2 GiB maximum image and 256 packed sections.

How the mapped image is reconstructed

  • Allocate a zeroed buffer of SizeOfImage bytes; copy the headers.
  • Copy every file-backed section to its virtual address in the buffer.
  • Rewrite each section header so SizeOfRawData = VirtualSize and PointerToRawData = VirtualAddress. This is the "RVA layout": file offset equals RVA.
  • For each table entry, decompress into the destination section. The writable span is the distance to the next section's start (or to SizeOfImage for the last), and it must be at least the section's virtual size. A block that decompresses to fewer bytes than the virtual size produces a warning, not an error.
  • The result is reparsed in memory (in_memory_reparsed); the CLI additionally reparses it from disk.
Analysis image, not a loadable file
The output is explicitly an analysis artifact. Producing a Windows-loadable file is a separate step in vmpx-rebuild (see PE reconstruction).

Detection & layout

Module: crates/vmpx-detect/src/lib.rs, function detect_vmprotect. Detection is a weighted evidence model: each finding adds points; the total (capped at 100) is the confidence. No single byte signature is required, and the file extension is ignored.

  • vmp_section_names (+20): sections whose lowercase name starts with .vmp. The code describes names as weak evidence "because they can be changed".
  • packed_virtual_sections (+25): three or more initialized virtual-only sections.
  • rva_mapped_analysis_image (+10): the image is already an RVA-layout analysis image.
  • high_entropy_entry_region (+20): the section owning the entry point has Shannon entropy at least 7.2 bits per byte.
  • entry_in_shared_protector_candidate (+5): the entry-owning section is both readable and executable.
  • multiple_high_entropy_executable_regions (+10): two or more executable sections at entropy 7.2 or higher.
  • imports_in_entry_region (+5) and exceptions_in_entry_region (+5): the import or exception directory lives inside the entry-owning executable section.
  • entry_and_tls_share_protector_region (+10): the entry point and the first TLS callback fall in the same executable region.

Verdict thresholds: 60 or more is VmprotectLikely, 30 or more is Suspicious, otherwise NoStrongEvidence. When the verdict is likely but no .vmp names exist, a warning says the classification is structural because randomized section names prevent name confirmation. The report also lists every executable section as an ExecutableRegion with its entropy and whether it owns the entry point.

Image-layout classification

The same pass classifies how the file is laid out (ImageLayout), which decides whether unpacking is needed:

  • RvaMappedAnalysisImage: at least 80% of sections have raw pointer = RVA and raw size = virtual size (the shape vmpx unpack produces).
  • PackedVirtualSections: otherwise, three or more initialized virtual-only sections.
  • ConventionalFile: otherwise, zero initialized virtual-only sections.
  • Ambiguous: anything else (one or two virtual-only sections).
Verified no-op
An input classified NoStrongEvidence with a ConventionalFile layout is the only case where vmpx clean clears its proof gate today; it copies the file unchanged.

The VM

Module family: crates/vmpx-vm/src/*. The code models a threaded-dispatch virtual machine: a virtual instruction pointer (VIP) walks encoded bytecode, a rolling key decodes it, and each decoded token steers a native handler that performs one operation on a VM stack (VSP) and context. VmContextLayout records the roles: VIP register, optional VSP register, rolling-key register, handler register, native-context register, context base register, allocation size, and bytecode direction.

Entry stubs

Modules: lib.rs (discover_vm_entries), entry_profile.rs, entry_paths.rs.

  • A virtualized routine is entered through a small native stub shaped push <immediate seed>; call <bootstrap>. The immediate is the per-entry seed; the call target begins the bootstrap.
  • Each candidate is scored by evidence: loader-reachable root (+10), immediate-seed push (+15), direct call (+15), the downstream chain saves at least 8 distinct registers (+15), saves flags (+5), reserves 0x80 to 0x1000 bytes of stack (+20), aligns the stack (+5), builds a pointer from a high aligned base (+5), performs state-dependent memory fetches (+5), ends in an indirect dispatch (+10). Entries need confidence 60 or more.
  • Roots are the PE entry point, every TLS callback, and (unless --no-scan) an executable scan of sections that own the entry point or have entropy at least 7.0, prefiltered on opcodes 0x68/0x6A (push imm) and validated by decoding.
  • Entries that reach the same stack-reservation instruction share a bootstrap and are grouped as one VmInstance; the set of distinct seeds per instance is recorded. inferred One protected binary can therefore contain several independently mutated VM instances.
  • Reachability is tracked: PE entry and TLS roots are LoaderReachable; scanned stubs are UnprovenExecutableCandidate.

Bootstrap and mutated register roles

Module: bootstrap.rs, native_context.rs.

  • The bootstrap saves the native state, builds the VM frame, and dispatches into the first handler. The code requires a saved native frame: all fifteen non-RSP general-purpose registers and unmodified RFLAGS must be saved before a full-width mov cursor, rsp capture. A "context scatter" then copies saved values into VM context slots; duplicate slots are legal and the last write wins.
  • Which native registers play VIP, rolling key, and handler differs per VM instance. The recovery therefore enumerates architectural role assignments and accepts only those that form a behaviorally valid dispatch slice. "No handler bytes, addresses, or fixed register allocation are assumed."
  • The terminal dispatch can be an indirect branch through a register or the equivalent push reg; ret; the code accepts both because "which one a given VM instance uses is a mutation, not a semantic difference".
  • The seed is evaluated concretely: a small concrete machine places it at [RSP+8] at the call target (the push before the call) and executes the bootstrap, yielding the initial VIP, initial rolling key, and handler anchor.
  • Bytecode direction can be ascending or descending (descending streams pre-decrement VIP before each read), and is a recovered property of the VM instance.

Dispatch extraction and handler slices

Modules: dispatch_extract.rs, handler_slice.rs, vmpx-disasm (trace.rs, dispatch_proof.rs).

  • The exception module comment states that "VMProtect scatters handler fragments across the image", so RVA order is not execution order. Handlers are traced as direct-jump fragment chains and linearized by control-flow reachability.
  • A conservative backward slice keeps only instructions that define live-out registers (the VIP, key, and handler registers) or flags. Memory accesses are kept; calls and exception-like transfers are barriers that retain all predecessors. Direct jumps that only connect fragments are labelled structural.
  • From the slice, every VIP-relative load is considered independently as a candidate relative-dispatch codec: how the next handler is computed from bytecode. Rejected candidates keep a diagnostic; none are guessed.
  • A postlude proof (prove_register_dispatch_postlude) shows that every direct-flow successor reaches a dispatch through the handler register without clobbering it, over a bounded state space (defaults: 50,000 states, stack depth 256).

The stateful decoder

Module: decoder.rs, transform.rs, codec_recovery.rs.

  • State is (VIP, rolling_key, handler) (RelativeDispatchState).
  • A KeyedTransformCodec decodes one value of a given width: optionally combine the encoded value with the low bits of the rolling key (add, sub, or xor, with the key on either side), apply a transform chain, then update the rolling key with the decoded value using a partial-width operation (only the low bits of the key change).
  • Transform operations the code models: Add, Sub, Xor, Not, Neg, Rol, Ror, Bswap (BSWAP is rejected at 8 bits). All are width-truncated and reversible.
  • One VM instruction is: decode an optional operand, then decode a signed displacement; the next handler is current_handler + sign_extended(displacement). The handler address is therefore never stored directly in bytecode. A handler may also set a static "handler base" anchor.
  • decode_linear_vm_stream runs until a stop condition: MissingHandlerSpec, ControlFlowBoundary, InvalidHandlerAddress, NativeHandlerError, BytecodeError, RepeatedState, InstructionLimit, or BytecodeSectionEscape. The last one encodes a fact about the VM: bytecode for a profile is confined to one section, so a VIP leaving it "proves the decoder state has drifted".
  • recover_and_decode_linear_vm_stream recovers each handler's codecs on demand, so no external handler table is required; an unresolved handler yields MissingHandlerSpec instead of an invented operation.

Operand and effect extraction

Modules: operand_extract.rs, effect_extract.rs, value_flow.rs, model.rs.

  • Operand codecs are recovered from VIP-relative load intervals, excluding loads already proven to be dispatch decodes. Cursor timing of a proven profile decides which load is which.
  • Handler effects are extracted from the semantic prefix of a handler (everything before the encoded-dispatch load): native memory reads/writes by region, VSP adjustment, arithmetic, and VM-visible flag effects. classify_handler_effects assigns a semantic only for families whose normalized shape is unambiguous; everything else stays Unknown with its evidence. prove_handler_value_flow adds def-use proof "shape agreement alone is not sufficient".
  • The recognized VmHandlerSemantic set: Dispatch, Push, Pop, ConstantPush, VirtualRegisterRead/Write, MemoryLoad/Store, TableChecksum, ReadTimestampCounter, UnsignedDivide, Add, Sub, Mul, Xor, And, Or, Nor, Nand, Not, Neg, shifts and rotates, Compare, Flags, SignExtend, ZeroExtend, StackAdjust, ConditionalBranch, UnconditionalBranch, NativeTransition, NativeCall, VmExit, ContextInitialize, Unknown.
  • Branches, native transitions, native calls and VM exit end a linear block (ends_linear_block); they are handled by the virtual-CFG explorer rather than the threaded decoder.
  • The expression folder encodes one VMProtect idiom explicitly: the pair not(not(x) + a) + b "expresses a plain pointer adjustment" and is folded to x + (b - a); without this, stack-relative addresses stay opaque.

The symbolic executor

Modules: semantic_exec.rs, expr.rs, symbolic_domain.rs, profile_explore.rs, profile_paths.rs, path_graph.rs, image_concretize.rs.

  • Decoded VM instructions are executed over a bit-vector expression IR (Expr, widths 8/16/32/64) with an exact byte-addressed memory model for the VM stack and external stores. Defaults: 4,096 instructions, 1 MiB of tracked memory, 200,000 expression nodes. Errors name the instruction and VIP; "it never guesses a missing operation".
  • A store to an address that could alias tracked memory discards precise memory ("havoc"). Unknown native calls also havoc tracked memory.
  • The profile explorer chains blocks: it follows same-profile virtual branches and native profile changes while carrying the full symbolic state, and "never guesses constraints or merges decoder states". Its stop reasons are SegmentLimit, TotalInstructionLimit, DecoderBoundary, ControlFlowBoundary, UnsupportedTransition, SymbolicTransitionTarget, AmbiguousProfileRoles, SymbolicExecutionFailure, and the successful VmExit.
  • Branches are resolved by finite input domains: the caller supplies explicit constant sets for symbolic inputs and every combination is run as an independent path (explore_vm_profile_paths). Missing domains leave an incomplete result. The clean pipeline uses one input, native_rdx_initial, over 0 to 3, for DLL entries (inferred the four DllMain reason codes); executable (non-DLL) entries are a stated blocker.
  • The path-graph assembler merges two nodes only when decoder state, profile roles, direction, the complete symbolic entry state, and block length are all equal.
  • Image-backed loads can be concretized, and recover_modulo_image_targets enumerates every residue of a W32 unsigned-division remainder to find all image-backed targets it selects. Callers must separately prove the referenced bytes are immutable.

Native transitions, native calls, and VM exit

Modules: native_call.rs, native_call_verify.rs, call_effects.rs, native_api.rs, vm_exit.rs, native_exit_state.rs, native_vm_chain.rs, native_continuation.rs.

  • Native-call bridge. A handler returns to native code to call an API, then resumes the VM. The recognizer proves the bridge shape by control-flow dominance and register/memory effects: load the call target into a register, save native RSP, call, store the return value, restore VSP, restore the saved VM registers, and complete a selector that picks one of several exhaustively proven outcomes before the threaded dispatch. A decoded selector with no proven outcome is an error.
  • Call summaries. A call target is matched against parsed imports (lookup values, IAT RVAs, and preferred-base IAT VAs all considered; duplicates are never collapsed). An unknown target has an Opaque memory effect, forcing a havoc. The trusted registry is deliberately narrow: LocalAlloc/GlobalAlloc (only with proven fixed flags, since MOVEABLE would return a handle), HeapAlloc, and CoTaskMemAlloc. Every dynamic call gets a unique epoch id so two identical calls are not assumed to return the same value.
  • VM exit. The epilogue is proven by requiring a VSP-to-native-RSP switch, restoration of every non-RSP general-purpose register from the stack, a final POPFQ, no non-stack memory access, and a native RET. Junk from register mutation is tolerated only if the final definition of each register is its corresponding POP.
  • Native exit state. The exact register, flags, and return-address values are read from the terminal symbolic memory snapshot; a restore-frame byte missing from the snapshot is an error.
  • VM-to-VM chaining. If the exit RET targets another VM entry stub, exploration continues by composing the next entry's frame, call continuation, flags, registers, and saved-stack cursor from the exact prior exit state.
  • Native continuation. After an exit that returns into ordinary native code, a bounded concrete/affine interpreter (defaults: 100,000 instructions, 64 KiB stack, 4 KiB C strings) follows it with a symbolic stack origin, records calls (resolving imports) and C-string arguments, and fails closed on unmodeled writes or unknown branches.
  • ReadTimestampCounter is a recognized handler (an rdtsc pushed as a split dword); it is represented as an opaque read_timestamp_counter_* intrinsic. The code does not assert its purpose.

Exception flow

Module: exception_flow.rs.

  • For a handler classified as a VM memory load, the external (non-VM-stack, non-context) read sites are collected as fault sites. Each is matched against the image's x64 exception table: a covering RUNTIME_FUNCTION whose UNWIND_INFO names a language-specific exception handler.
  • Each such language handler is analyzed as a stack sled builder. The recognizer requires it to load CONTEXT.Rsp (offset 0x98) through the context argument in R8, then copy a continuation seed and a validated ret gadget through a cursor to build a bounded virtual-unwind stack. Classification is by register/memory effects and control flow, not by bytes or addresses.
  • Three continuation sources are modeled: a non-zero seed, cursor memory, and a zero-seed unwind in which the stack is filled with RET gadgets and control unwinds through the original native frame to the caller's saved return address (no dispatch address exists on that path).
  • inferred The mechanism means a faulting read inside a handler can be an intended control-flow path: execution continues through an exception handler rather than falling through. The code reports whether all external reads route through language handlers and whether continuations are recovered, and refuses to claim a continuation without an exact pre-fault state.

Checksum and integrity handlers

Modules: checksum.rs, checksum_handler.rs, semantic_exec.rs.

  • The VM has a handler, TableChecksum, described in the source as a "recovered byte-at-a-time table checksum over program memory". inferred This is the VM-side implementation of VMProtect's self-integrity checking; the code recovers the arithmetic but does not itself state the protector's intent.
  • Contract (TableChecksumMetadata): a 32-bit accumulator seeded from a constant or from the VM stack, XORed with initial_xor; a pointer and length taken from VM-stack offsets, walked with a signed pointer_stride; per byte, a table index (accumulator & 0xFF) XOR input_byte into a 256-entry 32-bit table at a fixed virtual address; the accumulator is shifted (logical left or right by shift_bits) and XORed with the table entry and an optional constant; after the loop an optional NOT, then final_xor; the result lands at a recovered VM-stack offset after a vsp_delta.
  • Only that exact recurrence is supported: validate() demands a W32 accumulator, a 256-entry table of W32 entries, a shift below 32, and a nonzero stride. inferred The shape matches a CRC-32 style computation.
  • Recognition. The analyzer finds a counted W32 byte-table loop in the native handler and proves that both the zero-length path and the loop-exit path converge on the same ordinary threaded-dispatch tail. Constants and register choices come from data flow; "no handler addresses, table contents, or mutation bytes are signatured".
  • Evaluation. With concrete pointer, length, and table, the symbolic executor computes the checksum exactly by reading the analyzed image's bytes (bounded by the memory limit). Otherwise it emits an opaque intrinsic, table_checksum_low_byte_xor_recurrence_w32, carrying the accumulator, pointer, length, table, shift, stride, and a memory-snapshot epoch.
  • Lifting. vmpx-vmlift lists TableChecksum as a required lowering capability but it is not in the implemented set, so a routine containing it is not reported codegen-ready.
Why integrity checks matter for rebuilds
inferred A checksum over program memory depends on the bytes it reads. Because the analysis evaluates it against the analyzed image, a rebuilt image whose bytes differ (appended section, redirected entry, relocated layout) would not reproduce the original checksum value if the checked range changed. The code keeps checksum results symbolic or image-derived rather than assuming they are constants for the output.

Lifting & recompilation

Modules: crates/vmpx-vmlift/src/*, crates/vmpx-recompile/src/*.

  • Lifting. lift_profile_chain turns a successfully executed profile chain into a compact semantic routine: "VM bytecode, handler addresses, rolling keys, and dispatch mechanics are absent; only expressions, ordered external effects, context outputs, and control targets remain". Effects are MemoryWrite, MemoryHavoc, and NativeCall. Each routine is marked path-specific; there is no CFG merge yet.
  • Readiness gate. audit_instructions / audit_profile_chain compute the lowering capabilities a routine needs (from WidthAwareIntegerBackend to NativeExitBridge), compare them with the implemented set, and report ready_for_codegen only when nothing is missing. Currently implemented: width-aware integer, unary, shift, resize, memory, and branch backends plus stack SSA lowering. Unknown semantics are issues.
  • Replacement function. A recovered entry path ends with an exact symbolic value for every native register. build_replacement lowers each value into the project IR, computing each through scratch registers into its own spill slot, and a single epilogue loads every slot into its destination register (safe because each load reads a slot and writes a register). Observable effects (stores, imported calls) are replayed before the epilogue; flag state is restored via RestoreFlags because a caller may branch on flags the routine set. When the exit continues into the protector's own native continuation, the function ends with a tail jmp to it after restoring registers.
  • Imports. Fresh-allocation intrinsics are lowered to a real imported call through the IAT slot; any intrinsic that cannot be resolved this way is refused. vm_flags_<op>_wN intrinsics are rewritten to plain arithmetic.
  • Back end. vmpx-recompile is a small width-aware integer IR (add/sub/mul/xor/and/or, not/neg, shifts and rotates, resize, load/store, spill, Win64 call, compare, branch, return, tail jump, flags restore). It validates ABI facts (register assignment, Win64 alignment and shadow space, one virtual register per physical register) before encoding with iced-x86 in a two-pass branch resolve; "unsupported operations and unsafe ABI states are rejected instead of approximated".
  • Dispatchers. emit_domain_dispatcher hand-encodes cmp reg, imm; je body per recovered input value, then jmp fallback, so no frame setup clobbers incoming registers. It exists because one VM entry can behave differently per input value; each finite-domain path gets its own body.

PE reconstruction

Module: crates/vmpx-rebuild/src/*. Every operation is a guarded transaction: the output is reparsed and checked before it is returned.

append_section / next_section_rva

Appends one file-backed section to a PE32+ image without moving existing bytes. Requires an unused 40-byte section-table slot before SizeOfHeaders and the first raw section, that the slack is all zero, that it does not overlap a data directory, and that no security (signature) directory exists, since certificate relocation is not implemented. next_section_rva reports where the section will land, so RVA-sensitive payloads (branch fixups, import tables) can be built first.

set_entry_point / set_tls_callback / reintegrate

set_entry_point requires the target RVA to be in an executable section and file-backed. set_tls_callback rewrites one slot of the TLS callback array with the same checks. reintegrate chains: append the payload section, apply the entry redirect, apply each TLS redirect, then run loader validation and record pass/fail as a flag without failing on an invalid result. It takes already-rendered bytes, so the crate has no code-generation dependency.

relayout_conventional

Converts an RVA-layout analysis image into a conventional file. Every section keeps its VirtualAddress, so no directory, relocation, or branch needs rewriting; only PointerToRawData and SizeOfRawData change. Zero-fill sections keep no raw data. The load-bearing property, tested explicitly: the bytes the loader maps are unchanged apart from the section header table. Limits: PE32+ only, at most 96 sections, no security directory, sections must not overlap. Protector sections are kept as evidence, so normalize_characteristics clears IMAGE_FILE_RELOCS_STRIPPED when a relocation directory exists so the loader still applies base relocations.

validate_for_loader

A parseable PE can still fail to load, so this walks every directory the loader walks and requires the referenced bytes to be present: the entry point is in an executable, file-backed section; import module names end in .dll and every symbol has a name or ordinal; the TLS callback array and each callback are file-backed; every relocation target is mapped; every non-forwarded export is file-backed. It returns counts for imports, exports, TLS callbacks, and relocations.

serialize_import_table / plan_import_reconstruction / install_import_directories

Builds a conventional eager import table at a caller-chosen section RVA: a null-terminated descriptor array, separate import-name tables, one contiguous IAT, aligned hint/name records, and DLL strings. Inputs are semantic specifications; no original layout RVAs or raw thunk values are trusted, and names are restricted to nonempty ASCII. plan_import_reconstruction maps each resolved source IAT slot to exactly one rebuilt slot (ImportSlotRemap) so a later stage can retarget references without name matching; duplicate source slots and symbols without a single name or ordinal identity are rejected. A missing hint is serialized as zero (loader resolution is by name). install_import_directories sets optional-header directories 1 and 12 and checks the reparsed import list equals the serialized one.

Layout is not devirtualization
A conventional relayout produces a loadable, structurally valid file that still contains every protector section and VM handler. The CLI says so on its output (conventional layout, not devirtualized). The import-table builder exists, but the clean report still lists "application import set is not proven independently reconstructed" as a blocker.
