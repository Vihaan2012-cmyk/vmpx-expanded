Command-Line Reference
======================

The ``vmpx`` binary has nine subcommands. They are the kebab-case names of the
variants of the clap ``Command`` enum in ``crates/vmpx-cli/src/main.rs``.

.. code-block:: console

    $ vmpx --help
    $ vmpx --version

Conventions
-----------

Input is identified by content
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Every subcommand parses its input as a PE image regardless of the file
extension. A file that is not a structurally parseable PE is rejected with
``<path> is not a supported, structurally parseable PE``.

Text and JSON output
~~~~~~~~~~~~~~~~~~~~

Wherever ``--json`` is accepted the output is a single pretty-printed JSON
document on standard output. Without it, a bracket-tagged text report is
printed. The tags identify the stage that produced each line:

.. list-table::
   :header-rows: 1
   :widths: 20 57

   * - Tag
     - Meaning
   * - ``[pe]``, ``[file]``
     - Image kind and path (``info``, ``verify``)
   * - ``[hash]``
     - SHA-256 of the input, uppercase hexadecimal
   * - ``[headers]``
     - Image base, entry RVA/VA, size of image
   * - ``[sections]``
     - One line per section
   * - ``[directories]``
     - Data directories
   * - ``[imports]``
     - Import module and symbol counts (``info``) or the IAT reference inventory (``imports``)
   * - ``[exports]``
     - Export count
   * - ``[tls]``
     - TLS callbacks
   * - ``[exceptions]``
     - x64 exception-table function count
   * - ``[relocations]``
     - Base relocation blocks and entries
   * - ``[verify]``
     - Result of structural validation or of reparsing a written file from disk
   * - ``[vmp]``
     - VMProtect detection verdict and weighted evidence
   * - ``[region]``
     - One line per executable section
   * - ``[vm]``
     - VM discovery summary, instances, entries and warnings
   * - ``[oep]``
     - Module-entry assessment
   * - ``[compare]``
     - Structural differences between two files
   * - ``[unpack]``
     - Packer table, blocks and loader validation
   * - ``[clean]``
     - Pipeline summary and blockers
   * - ``[decode]``
     - One line per recovered VM path
   * - ``[layout]``
     - Conventional relayout and loader validation
   * - ``[experimental]``
     - Experimental-output notices
   * - ``[report]``
     - Path of a written JSON report

Every JSON document carries a ``schema_version`` field so that consumers can
detect format changes. Addresses are serialized as plain integers (an ``Rva``
is a ``u32``, a ``Va`` and an ``ImageBase`` are ``u64``); the text reports
render them as ``0x`` prefixed uppercase hexadecimal.

Exit status
~~~~~~~~~~~

A subcommand exits ``0`` on success and non-zero on any error. Two conditions
are worth knowing about because they are deliberate:

* ``verify`` prints its report and then fails if the report contains any
  diagnostics.
* ``clean`` fails when the proof gate refuses output
  (``clean proof gate refused <input>; output <output> was not written``). The
  report, if requested, is written *before* the failure.

Write safety
~~~~~~~~~~~~

Commands that write files refuse to overwrite their input, directly or through
an alias (a different path that resolves to the same file). ``clean``
additionally refuses if the output already exists, and refuses if ``--report``,
``--reconstructed`` or ``--experimental`` alias the input, the output, or each
other. Every file written is reparsed from disk before the command reports
success.
